# T109 — cache dei prompt Anthropic per i subagent

> **INBOX**: nozioni · indexed · drainable
> **TLDR**: comportamento della cache prompt Anthropic per i subagent Claude Code — cosa sta nel prefisso cachabile (body dell'agent) e cosa no (prompt d'invocazione, contesto progetto), minimi per modello, TTL, fan-out, fork, e come misurare dai transcript.

- **n1** — La cache dei prompt Anthropic è un prefix-match sui byte esatti con ordine di resa `tools → system → messages`: per un subagent il body dell'agent (contratti iniettati inline compresi) è il prompt di system, costante e quindi cachabile fra spawn dello stesso tipo, mentre il prompt d'invocazione è il primo messaggio user e sta dopo il breakpoint — varia liberamente senza invalidare la cache, quindi il path o il payload per-invocazione viaggiano lì. Su Haiku 4.5 il prefisso minimo cachabile è 4.096 token e sotto quella soglia la cache non parte, in silenzio; il TTL è 5 minuti (1 ora costa il doppio in scrittura); lettura ~0,1× del prezzo input, scrittura 1,25×, pareggio alla seconda invocazione. Ancora: ridurre il costo di spawn ripetuti di un subagent / cachare i contratti di un agent di plugin.
- **n2** — Un subagent apre una conversazione propria, con system prompt e tool set propri, quindi non legge la cache del parent e ne scalda una sua; il body dell'agent sta dentro quel system prompt, ed è il motivo per cui un contratto iniettato inline nel body è cachabile fra spawn dello stesso tipo. Due asimmetrie da conoscere: il TTL di un subagent è 5 minuti anche su abbonamento, dove la sessione principale usa automaticamente quello a 1 ora, e nei fan-out di agenti con lo stesso prefisso il CLI trattiene da sé tutti gli spawn tranne il primo, così che gli altri leggano il prefisso appena scritto invece di pagarlo tutti pieno. Un fork è il caso opposto del subagent: eredita system prompt, tool e storia del parent alla lettera, quindi la sua prima richiesta legge la cache del parent. Ancora: cachare i contratti di un agent di plugin / capire perché un subagent non riusa la cache della sessione.
- **n3** — Il body di un agent di plugin sta dentro il prefisso cachabile del subagent, quindi un contratto iniettato inline nel body viene riletto dalla cache fra due spawn distinti dello stesso agent, mentre il prompt d'invocazione può variare liberamente. La prova è differenziale e serve per intero, perché il solo confronto fra due spawn uguali non distingue il body dalle tool definitions comuni: spawnando lo stesso agent due volte con prompt diversi il secondo rilegge una quota del prefisso, ma spawnando un agent diverso con lo stesso identico tool set la rilettura torna a zero — cioè il segmento riletto dipende dall'identità del body, non dai tool. La quota riletta è però solo un terzo circa del totale: il resto è il contesto di progetto che il subagent riceve, e che sta oltre l'ultimo breakpoint — quindi la potatura di un contratto incide solo sul terzo cachabile, mentre il pavimento per-spawn resta. Ancora: decidere se iniettare un contratto inline nel body di un agent / stimare il costo reale di uno spawn di subagent.
- **n4** — Il consumo di cache di un subagent è misurabile a posteriori senza strumenti dedicati: ogni subagent ha un transcript proprio in `~/.claude/projects/<hash-cwd>/<session-id>/subagents/agent-<id>.jsonl`, e ogni record `type:assistant` porta `message.usage` coi campi `cache_creation_input_tokens` e `cache_read_input_tokens`. Ne discende un test deterministico per sapere se i contratti iniettati inline nel body di un agent stanno davvero nel prefisso cachabile: si spawna l'agent due volte entro il TTL di 5 minuti variando solo il prompt d'invocazione, e si confronta il primo record assistant dei due spawn — se il `cache_read` del secondo è almeno pari al `cache_creation` del primo, il prefisso ha fatto match e la parte variabile è caduta dopo il breakpoint come deve. Un `cache_creation` pari a zero già al primo spawn dice invece che il prefisso sta sotto il minimo cachabile, e distingue quella causa dal prefisso che differisce fra spawn, che mostra creation alto e read a zero. Ancora: verificare che un contratto inline nel body di un agent sia cachato / misurare il costo reale di uno spawn ripetuto.
- **n5** — Il caching dei subagent ha un difetto segnalato e non chiuso: l'issue anthropics/claude-code#29966 riporta che il path dei subagent forza `enablePromptCaching` a `false`, quindi le loro richieste partono senza nessun blocco `cache_control` e ogni spawn ripaga tools e system a prezzo pieno. La misura diretta sui transcript smentisce però il difetto su versioni recenti del CLI — dentro una singola invocazione il `cache_read` cresce da 0 a decine di migliaia di token fra un turno e il successivo — quindi il difetto va verificato sulla propria versione invece che assunto, e la verifica che conta per un contratto inline è quella fra due spawn distinti, non fra i turni di uno solo. Ancora: sospettare che un subagent non stia cachando / valutare quanto rende un contratto inline nel body di un agent.
